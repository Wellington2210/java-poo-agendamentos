REVISÃO DE JAVA E POO — PARA QUEM NUNCA VIU ISSO

Construindo o sistema de agendamentos da barbearia

Se você nunca programou orientado a objetos, comece pela seção 0. O material vai crescendo do básico (classe, objeto) até os quatro pilares da POO e a modelagem completa do projeto: Pessoa, Cliente, Profissional, Serviço e Agendamento.

antes de tudo

O que é, afinal, "orientação a objetos"?

Imagine a barbearia funcionando só no papel. Toda vez que um cliente marca um horário, o dono pega uma ficha em branco e preenche: nome do cliente, serviço, data, horário. Cada cliente novo ganha uma ficha nova — as fichas não se misturam.

Programação orientada a objetos (POO) é exatamente essa ideia dentro do computador: a ficha em branco (o modelo que diz quais campos existem) é uma classe; cada ficha preenchida é um objeto.

POR QUE ISSO IMPORTA Sem POO, o código viraria uma bagunça de variáveis soltas (nomeCliente1, nomeCliente2...). A classe agrupa tudo que pertence a "um agendamento" num único lugar, e cada objeto é uma cópia independente dessa estrutura.
PARTE 1

Fundamentos

Classe, objeto, atributos, métodos, parâmetros e o this — o vocabulário básico que aparece em praticamente toda linha de código Java orientado a objetos.

01 · fundamentos

Classe

Uma classe é o molde usado para criar objetos. Ela só descreve quais informações um objeto vai ter — sozinha, ela não representa nada concreto ainda.

PENSE ASSIM A classe é a ficha impressa em branco, com os campos "Nome: ____", "Preço: ____". Ninguém preencheu nada ainda — é só o formulário.
public class Servico { private String nome; private double preco; }
Servico ├── nome └── preco

A classe define quais informações e comportamentos os objetos desse tipo poderão ter — o preenchimento vem depois.

02 · fundamentos

Objeto

O objeto é uma ficha preenchida, criada a partir da classe com a palavra new. Cada new reserva um espaço novo na memória — um objeto totalmente independente dos demais.

Servico servico = new Servico("Corte", 40);
Servico
o tipo — diz que a variável vai guardar um objeto desse molde.
servico
o nome que demos à variável — um "rótulo" que aponta para o objeto criado.
new Servico(...)
o comando que efetivamente cria o objeto na memória.
O ponto mais importante: se você criar dois objetos a partir da mesma classe, cada um vive de forma separada — alterar um não afeta o outro.
Servico servico1 = new Servico("Corte", 40); Servico servico2 = new Servico("Barba", 30);
servico1 → objeto A (Corte, R$40)
servico2 → objeto B (Barba, R$30)
Se você mudar o preço de servico1, o que acontece com servico2? testar
Nada. São objetos diferentes, cada um com sua própria cópia dos atributos — mudar um não tem qualquer efeito sobre o outro, mesmo vindo da mesma classe.
03 · fundamentos

Atributos e métodos

Atributos são os dados guardados dentro de um objeto — o que ele tem. Métodos são as ações que o objeto sabe executar — o que ele faz.

private String nome; private double preco; // nome = "Corte" // preco = 40.00
public void reagendar(String novoHorario) { this.horario = novoHorario; }

04 · fundamentos

Parâmetros

Um método (ou um construtor, como veremos mais à frente) pode receber informações de fora através de um parâmetro — uma variável temporária que só existe durante a execução daquele bloco.

public void reagendar(String novoHorario) { this.horario = novoHorario; } // uso: agendamento.reagendar("14:30");
"14:30"
→
novoHorario
→
this.horario
05 · fundamentos

this

this representa o objeto atual. Ele existe principalmente para diferenciar o atributo do objeto de um parâmetro que tenha o mesmo nome.

this.nome = nome; // ↑ ↑ // atributo parâmetro

this é sempre obrigatório?

Não. Em um getter simples, sem nenhum parâmetro de mesmo nome por perto, o Java não fica em dúvida — então tanto faz escrever com ou sem this:

public String getHorario() { return horario; } // funciona igual a: public String getHorario() { return this.horario; }

Já no construtor, onde o parâmetro costuma ter o mesmo nome do atributo, o this deixa de ser opcional:

public Agendamento(String horario) { this.horario = horario; }
Por que o this não faz diferença no getter, mas faz diferença no construtor? testar
No getter não existe nenhum parâmetro chamado horario — só o atributo. Sem ambiguidade, o Java entende horario sozinho como o atributo. Já no construtor existem dois horario ao mesmo tempo (o parâmetro e o atributo), e é o this. que aponta explicitamente para o atributo do objeto.
PARTE 2

Encapsulamento

O primeiro dos quatro pilares da POO: o objeto protege seu estado interno e decide como ele pode ser lido ou alterado.

06 · encapsulamento

public e private

São modificadores de acesso. public pode ser acessado de qualquer lugar do programa. private só pode ser acessado diretamente dentro da própria classe.

PENSE ASSIM public é deixar a ficha em cima do balcão — qualquer funcionário mexe. private é guardar numa gaveta trancada — só a própria recepção (a própria classe) tem a chave.
private String nome; // em outra classe, isto não funciona: cliente.nome = "João";
07 · encapsulamento

Getter e setter

Se um atributo é private, o getter é a porta de saída (para ler o valor) e o setter é a porta de entrada (para alterá-lo) — os dois na forma de métodos públicos.

public String getNome() { return this.nome; } public void setNome(String nome) { this.nome = nome; } // uso: cliente.getNome(); cliente.setNome("João");

Mas não somos obrigados a criar um setter para todo atributo — isso fica mais claro nas próximas duas seções.

08 · encapsulamento

Encapsulamento

Encapsulamento significa proteger e controlar o estado interno do objeto. Em vez de deixar qualquer parte do programa alterar um atributo livremente...

agendamento.horario = "14:30"; // direto assim, sem nenhuma verificação

...criamos uma operação com nome e com regras:

public void reagendar(String novoHorario) { if (novoHorario == null) { return; } this.horario = novoHorario; }

Esse pequeno if já é uma regra de negócio. No futuro, esse mesmo método pode crescer com mais verificações sem que o resto do sistema precise mudar.

09 · encapsulamento

Por que nem tudo precisa de setter?

Poderíamos ter criado setHorario(...). Mas no nosso sistema faz mais sentido ter reagendar(...), porque esse nome representa uma operação real do negócio — e não apenas uma troca crua de valor.

public void reagendar(String novoHorario) { // verificar se está cancelado // verificar disponibilidade // verificar data this.horario = novoHorario; }
A ideia geral fica assim:
Construtor → cria o estado inicial.
Getter → permite consultar.
Método específico (como reagendar) → altera seguindo regras.
Por que não deixar agendamento.horario = "14:30" direto, se no fim o valor é o mesmo? testar
Porque, alterando direto, nenhuma regra de negócio seria aplicada — qualquer parte do sistema poderia gravar um horário inválido ou de um agendamento já cancelado. Passando por reagendar(), a própria classe garante que essas verificações aconteçam sempre.
PARTE 3

Construtores

Como um objeto nasce já pronto, com que regras isso funciona, e o que acontece quando um objeto muda depois de criado.

10 · construtores

Construtor

O construtor inicializa o objeto — ele nasce já com os dados corretos.

public Servico(String nome, double preco) { this.nome = nome; this.preco = preco; } // uso: Servico servico = new Servico("Corte", 40);
new Servico(...)
→
construtor
→
nome = "Corte", preco = 40
11 · construtores

Construtor não é um método comum

Método

public void reagendar(String h) { } // tem retorno (void)

Construtor

public Agendamento(...) { } // sem tipo de retorno

O construtor não possui tipo de retorno, e possui exatamente o mesmo nome da classe.

12 · construtores

Construtor padrão

Se nenhum construtor for escrito, o Java fornece implicitamente um construtor vazio equivalente a:

public Cliente() { }
Pegadinha comum: assim que você escreve manualmente um construtor com parâmetros, o Java deixa de fornecer o construtor vazio automaticamente.
public Cliente(String nome) { } // agora new Cliente() sem argumentos dá erro, // a não ser que você declare os dois construtores
13 · construtores

Sobrecarga

Métodos ou construtores podem ter o mesmo nome, desde que os parâmetros sejam diferentes. O Java escolhe qual usar pelos argumentos fornecidos.

public Agendamento() { } public Agendamento(String horario) { } public Agendamento(String data, String horario) { }
14 · construtores

Mudança de estado

Um objeto pode mudar depois de criado, sem que isso crie um objeto novo — é o mesmo objeto, só que com um valor diferente guardado dentro dele.

// inicialmente: horario = 09:10 agendamento.reagendar("14:30"); // agora: horario = 14:30
Depois do reagendar, quantos objetos Agendamento existem? testar
Ainda apenas um. Nenhum new foi chamado — só o valor de um atributo mudou dentro do objeto que já existia.
PARTE 4

Herança

O segundo pilar: como criar uma relação de tipo "isto é um caso mais específico daquilo".

15 · herança

"É UM" e extends

Herança representa a relação "é um". No nosso projeto: um Cliente é uma Pessoa. Um Profissional também é uma Pessoa. Ambos compartilham dados em comum (nome, e-mail), mas cada um tem seu próprio comportamento.

PENSE ASSIM "Pessoa" é a categoria geral — como "veículo". "Cliente" e "Profissional" são versões mais específicas — como "carro" e "moto": os dois são veículos, mas cada um também tem características próprias.
public class Cliente extends Pessoa { } public class Profissional extends Pessoa { }

A palavra extends é o que cria essa relação — ela diz "esta classe é uma especialização daquela outra".

16 · herança

super

Pessoa tem um construtor que recebe nome e e-mail. Como Cliente herda de Pessoa, ele precisa de um jeito de repassar esses dados para o construtor da classe "mãe" — é isso que super(...) faz.

public Pessoa(String nome, String email) { this.nome = nome; this.email = email; }
public Cliente(String nome, String email) { super(nome, email); }
new Cliente(...)
→
construtor Cliente
→
super(nome, email)
→
construtor Pessoa
→
nome e email inicializados
17 · herança

Métodos herdados

Pessoa já tem getNome(). Como Cliente herda de Pessoa, ele ganha esse método de graça — sem precisar reescrevê-lo.

// dentro de Pessoa: public String getNome() { return this.nome; } // funciona mesmo sem declarar getNome() em Cliente: cliente.getNome();
PARTE 5

Polimorfismo

O terceiro pilar: tratar objetos diferentes através de um tipo em comum, e deixar cada um reagir do seu próprio jeito.

18 · polimorfismo

Polimorfismo

Uma referência de um tipo mais geral pode apontar para um objeto de um tipo mais específico.

Pessoa pessoa1 = new Cliente("Wellington", "email"); Pessoa pessoa2 = new Profissional("Marina", "email");
Pessoa pessoa1
o tipo declarado da variável — mais geral.
new Cliente(...)
o objeto real criado na memória — mais específico.
PENSE ASSIM É como guardar um "carro" e uma "moto" numa lista rotulada só de "veículo". Você pode tratar os dois de forma genérica (como veículos), mesmo sabendo que, por baixo, cada um é uma coisa diferente.
19 · polimorfismo

Sobrescrita e @Override

Pessoa pode ter um método genérico apresentar(). Cada classe filha pode fornecer sua própria versão — isso é sobrescrita.

public void apresentar() { } // em Cliente: @Override public void apresentar() { System.out.println("Eu sou cliente"); } // em Profissional: @Override public void apresentar() { System.out.println("Eu sou profissional"); }

@Override é apenas uma anotação — ela avisa o Java (e quem lê o código) que essa é intencionalmente uma nova implementação de um método que já existia na classe mãe. Se o nome não bater com nenhum método herdado, o Java aponta erro, o que ajuda a evitar erros de digitação.

20 · polimorfismo

Sobrecarga × sobrescrita

Os nomes parecem sinônimos, mas são conceitos bem diferentes.

Sobrecarga (overload)

Mesmo nome + parâmetros diferentes, na mesma classe.
Agendamento() Agendamento(String horario)

Sobrescrita (override)

Herança + mesmo método + nova implementação, em uma classe filha.
Pessoa.apresentar() Cliente.apresentar()
PARTE 6

Abstração

O quarto pilar: criar conceitos gerais demais para existir sozinhos, e obrigar as classes filhas a preencherem os detalhes.

21 · abstração

Classe abstrata

Pessoa, sozinha, representa só um conceito geral demais para existir de verdade no nosso sistema — nunca vamos cadastrar "uma pessoa genérica", só clientes ou profissionais. Por isso ela vira uma classe abstrata.

public abstract class Pessoa { }

Uma classe abstrata não pode ser instanciada diretamente:

Pessoa pessoa = new Pessoa(...); // erro de compilação Pessoa pessoa = new Cliente(...); // funciona: o objeto real é Cliente
22 · abstração

Método abstrato

Dentro de Pessoa, podemos declarar um método sem implementação nenhuma:

public abstract void apresentar();

Isso não tem chaves { } porque não existe implementação ali — a implementação real fica por conta de cada classe filha. É uma forma de dizer:

"Toda classe concreta que herdar de Pessoa é obrigada a implementar apresentar() do seu próprio jeito."
23 · síntese

Os quatro pilares que estudamos

PARTE 7

Associação

Nem toda relação entre classes é herança. Muitas vezes um objeto simplesmente guarda uma referência para outro — é isso que conecta Agendamento, Cliente, Profissional e Servico.

24 · associação

"TEM UM"

Associação é quando um objeto se relaciona com outro objeto, guardando-o como atributo. No nosso projeto: um Agendamento tem um Cliente, tem um Serviço, tem um Profissional.

public class Agendamento { private Cliente cliente; private Servico servico; private Profissional profissional; }
Não confunda com herança: "Cliente é uma Pessoa" é herança (extends). "Agendamento tem um Cliente" é associação (um atributo do tipo Cliente). São perguntas diferentes que levam a soluções diferentes.

É UM → herança

class Cliente extends Pessoa

TEM UM → associação

private Cliente cliente;
25 · associação

Nossas próprias classes também são tipos

Já usamos tipos prontos do Java como String, int e double. Mas quando criamos public class Cliente { }, Cliente também vira um tipo válido — por isso podemos escrever private Cliente cliente; normalmente.

private Cliente cliente; // ↑ ↑ ↑ // acesso tipo nome

Leitura em voz alta: "o objeto Agendamento possui um atributo privado chamado cliente, capaz de guardar uma referência para um objeto Cliente."

Por que criamos uma classe Servico?

Poderíamos ter usado só private String servico;, guardando apenas "Corte". Mas um serviço de verdade tem várias informações (nome, preço, duração...) — então faz mais sentido que Servico seja sua própria classe, e não apenas um texto solto.

26 · associação

Referência, não cópia

Quando o construtor do Agendamento recebe um Cliente e faz this.cliente = cliente;, ele não copia os dados do cliente (nome, e-mail) para dentro de si. Ele guarda uma referência — um "endereço" que aponta para o objeto Cliente que já existe em outro lugar da memória.

public Agendamento( Cliente cliente, Servico servico, Profissional profissional, String data, String horario) { this.cliente = cliente; this.profissional = profissional; this.servico = servico; this.data = data; this.horario = horario; }
Agendamento ┌──────────────┐ │ │ cliente ───────┤ cliente │ │ │ servico ───────┤ servico │ │ │ profissional ──┤ profissional │ │ │ │ data │ │ horario │ └──────────────┘

E o getter que devolve esse atributo não devolve um texto — devolve o próprio objeto:

public Cliente getCliente() { return this.cliente; }
27 · associação

Encadeamento de métodos

Como getCliente() devolve um objeto Cliente, podemos chamar imediatamente outro método nesse objeto devolvido, tudo na mesma linha:

agendamento.getCliente().getNome();
Agendamento
→
getCliente()
→
Cliente
→
getNome()
→
"Wellington"

Essa linha é só um atalho para dois passos separados — o resultado é idêntico:

Cliente clienteDoAgendamento = agendamento.getCliente(); String nome = clienteDoAgendamento.getNome();

O mesmo vale para agendamento.getServico().getPreco(), ou qualquer outra combinação entre objetos associados.

28 · associação

Por que não usamos setters aqui?

O construtor já cria o Agendamento completo, com cliente, serviço e profissional definidos de uma vez. Não é necessário permitir setCliente(), setServico() ou setProfissional() soltos — em vez disso, criamos operações com significado real, como reagendar(), cancelar() ou trocarProfissional(), e colocamos as regras de negócio dentro delas.

PARTE 9

Status, null e datas reais

Antes de sair do Java puro, faltam três peças para o agendamento virar algo realista: o que fazer quando não existe objeto nenhum, um jeito de limitar os estados possíveis, e datas de verdade em vez de texto solto.

31 · status e datas reais

null e NullPointerException

null é um valor especial que significa "esta referência não aponta para nenhum objeto agora". Não é um objeto vazio, nem um texto vazio — é a ausência de objeto.

Cliente cliente = null;

O problema aparece quando você tenta chamar um método nessa referência vazia:

Cliente cliente = null; cliente.getNome(); // gera: NullPointerException
PENSE ASSIM É como pedir pra alguém ler o nome escrito numa ficha que ainda não existe. Não existe ficha nenhuma pra ler — o programa trava porque a instrução não faz sentido.

Por isso é comum verificar antes de usar:

if (novaDataHora == null) { return; }

Essa é exatamente a verificação que já aparecia dentro de reagendar() lá na seção 8 — agora você sabe por que ela existe: sem ela, passar null como novo horário derrubaria o programa.

32 · status e datas reais

enum e regras de status

Um enum representa um conjunto limitado de opções possíveis — diferente de uma String, que aceitaria qualquer texto digitado.

public enum StatusAgendamento { AGENDADO, CANCELADO, CONCLUIDO }

StatusAgendamento também vira um tipo, do mesmo jeito que Cliente ou Servico viraram — por isso dá pra usá-lo como tipo de atributo:

private StatusAgendamento status; // todo novo agendamento nasce assim: this.status = StatusAgendamento.AGENDADO;

String

Aceita qualquer texto: "agendadoo", "xyz"... nada impede um erro de digitação.

enum

Só existem os valores declarados. Também dá pra comparar com == em vez de .equals().

Combinando enum com if, criamos regras de negócio de verdade — por exemplo, impedir que um agendamento já cancelado seja concluído:

public void cancelar() { if (this.status == StatusAgendamento.CANCELADO) { return; } if (this.status == StatusAgendamento.CONCLUIDO) { return; } this.status = StatusAgendamento.CANCELADO; }
AGENDADO / \ / \ cancelar() concluir() ↓ ↓ CANCELADO CONCLUIDO
Repare que não existe caminho de CANCELADO para CONCLUIDO, nem o contrário — uma vez que o agendamento chega a um desses dois estados finais, ele para ali.
33 · status e datas reais

LocalDateTime e formatação

Até agora, data e horario eram textos soltos ("07/10", "09:10"). Isso funciona pra estudar, mas um sistema de verdade precisa de um tipo pensado pra representar datas — o LocalDateTime, que já vem pronto no Java.

private LocalDateTime dataHora; // criando uma data específica: LocalDateTime dataHora = LocalDateTime.of(2026, 12, 25, 20, 30); // representa: 25/12/2026 às 20:30

Como LocalDateTime guarda a data de um jeito interno, não exatamente igual ao que uma pessoa lê, usamos um DateTimeFormatter pra exibir no formato desejado:

DateTimeFormatter formato = DateTimeFormatter.ofPattern("dd/MM/yyyy HH:mm"); agendamento.getDataHora().format(formato); // resultado: "25/12/2026 20:30"
34 · status e datas reais

Agendamento atualizado

Juntando o enum de status e o LocalDateTime, a classe Agendamento fica assim:

public class Agendamento { private Cliente cliente; private Servico servico; private Profissional profissional; private StatusAgendamento status; private LocalDateTime dataHora; public Agendamento(Cliente cliente, Servico servico, Profissional profissional, LocalDateTime dataHora) { this.cliente = cliente; this.profissional = profissional; this.servico = servico; this.dataHora = dataHora; this.status = StatusAgendamento.AGENDADO; } public Cliente getCliente() { return this.cliente; } public Servico getServico() { return this.servico; } public Profissional getProfissional() { return this.profissional; } public LocalDateTime getDataHora() { return this.dataHora; } public StatusAgendamento getStatus() { return this.status; } public void reagendar(LocalDateTime novaDataHora) { if (novaDataHora == null) { return; } this.dataHora = novaDataHora; } public void concluir() { if (this.status == StatusAgendamento.CANCELADO) { return; } if (this.status == StatusAgendamento.CONCLUIDO) { return; } this.status = StatusAgendamento.CONCLUIDO; } public void cancelar() { if (this.status == StatusAgendamento.CANCELADO) { return; } if (this.status == StatusAgendamento.CONCLUIDO) { return; } this.status = StatusAgendamento.CANCELADO; } }
Pessoa (abstract) ├── Cliente └── Profissional Servico StatusAgendamento ├── AGENDADO ├── CANCELADO └── CONCLUIDO Agendamento ├── Cliente ├── Profissional ├── Servico ├── LocalDateTime └── StatusAgendamento
PARTE 10

Collections: List e ArrayList

Até agora cada agendamento vivia sozinho, numa variável separada. Chegou a hora de guardar vários de uma vez — clientes, profissionais, agendamentos — dentro de uma única coleção.

35 · collections

List e ArrayList

Uma List serve para guardar vários elementos do mesmo tipo, em ordem.

List<Agendamento> agendamentos;

Leia: "uma lista que guarda objetos do tipo Agendamento." Criamos a lista assim:

import java.util.List; import java.util.ArrayList; List<Agendamento> agendamentos = new ArrayList<>();
List<Agendamento>
o tipo da variável — uma lista que só aceita objetos Agendamento dentro dela.
agendamentos
o nome que demos à lista.
new ArrayList<>()
cria a lista de fato — vazia, pronta para receber itens.
PENSE ASSIM Se List é a ideia geral de "uma fila de fichas", ArrayList é o tipo específico de pasta que estamos usando para organizar essa fila. Por enquanto, pense em List como o rótulo e ArrayList como a implementação concreta que escolhemos — a diferença entre interface e implementação fica mais clara mais adiante.
36 · collections

add(), size() e índices

add() coloca um elemento no fim da lista. As posições dentro de uma lista começam a contar do 0, não do 1 — isso é chamado de índice.

agendamentos.add(agendamentoWellington); agendamentos.add(agendamentoBruno); agendamentos.add(agendamentoLucas);
Wellington
[0]
Bruno
[1]
Lucas
[2]

size() devolve quantos elementos existem na lista agora:

int quantidade = agendamentos.size(); // quantidade = 3
37 · collections

get() e encadeamento

get(posição) devolve o elemento que está naquele índice.

Agendamento primeiro = agendamentos.get(0); // primeiro → o Agendamento do Wellington

E como já sabemos encadear métodos (seção 27), podemos ir direto do índice até um dado específico, tudo numa linha:

agendamentos.get(0).getCliente().getNome();
Lista
→
get(0)
→
Agendamento
→
getCliente()
→
getNome()
→
"Wellington"
38 · collections

remove() e cuidado com posições

remove() aceita um índice ou o próprio objeto:

agendamentos.remove(1); // remove pela posição 1 (Bruno) agendamentos.remove(agendamentoLucas); // remove pedindo aquele objeto específico
Wellington
[0]
Bruno
[1]
Lucas
[1] agora

Repare: depois de remover o índice 1, o que era [2] (Lucas) desliza e passa a ser [1] — a lista se reorganiza automaticamente.

Cuidado: pedir uma posição que não existe (agendamentos.get(10) numa lista de 3 itens) gera um IndexOutOfBoundsException — parecido em espírito com o NullPointerException, mas para posições inválidas em vez de referências vazias.
39 · collections

for-each

Em vez de chamar get(0), get(1), get(2) manualmente, o for-each percorre a lista inteira sozinho.

for (Agendamento item : agendamentos) { // item recebe, um de cada vez, cada Agendamento da lista }

Leia: "para cada Agendamento dentro de agendamentos, coloque temporariamente esse objeto em item."

1ª volta: item → Wellington
→
2ª volta: item → Bruno
→
3ª volta: item → Lucas
Erro clássico: um ponto e vírgula sobrando depois do for-each — for (...) ; { } — encerra o laço ali mesmo, e o bloco entre chaves nunca roda de verdade dentro dele. Fique de olho nesse ; a mais.
40 · collections

for-each + enum + if

Agora dá pra combinar tudo que já vimos: percorrer a lista, olhar o status de cada agendamento, e agir só nos que interessam.

for (Agendamento item : agendamentos) { if (item.getStatus() == StatusAgendamento.AGENDADO) { System.out.println(item.getCliente().getNome()); } }

Esse pequeno trecho já junta List, for-each, objetos, getter, enum e if — praticamente tudo que estudamos até aqui, trabalhando junto.

41 · collections

Mesma referência, vários agendamentos

Não precisamos criar um objeto Profissional novo pra cada agendamento da Marina — o mesmo objeto pode ser reaproveitado em vários agendamentos diferentes.

Profissional marina = new Profissional("Marina", "marina@gmail.com"); Agendamento a1 = new Agendamento(cliente1, servico1, marina, dataHora1); Agendamento a2 = new Agendamento(cliente2, servico2, marina, dataHora2);
Agendamento Wellington ──┐ │ Agendamento Bruno ───────┼──► Marina │ Agendamento Lucas ───────┘

Os três agendamentos guardam referências diferentes para o mesmo objeto Marina — reforçando o que vimos na seção 26: associação guarda um "endereço", não uma cópia.

42 · collections

Lista hoje × banco de dados depois

Hoje criamos os objetos manualmente e usamos add() pra colocá-los numa lista. Mais adiante, quando o banco de dados entrar em cena, quem vai preencher essa lista será o próprio banco:

// hoje: List<Agendamento> agendamentos = new ArrayList<>(); agendamentos.add(agendamento); // no futuro, com Spring + JPA: List<Agendamento> agendamentos = agendamentoRepository.findAll();

Ainda não estudamos Repository nem JPA — esse exemplo só serve pra mostrar por que aprender List agora continua valendo depois: o formato final (uma lista de objetos Agendamento) é o mesmo, só muda de onde os dados vêm.

43 · collections

Introdução a Object

Object é a classe que fica no topo de toda hierarquia em Java. Quando você escreve public class Servico { }, é como se por baixo dos panos existisse:

public class Servico extends Object { }
Object ├── Pessoa │ ├── Cliente │ └── Profissional │ ├── Servico └── Agendamento

É por causa disso que todo objeto Java, mesmo sem você escrever nada a mais, já vem com alguns métodos de fábrica: toString(), equals(), hashCode() e getClass().

Ainda não vamos fundo nesses métodos — essa é só a introdução. toString(), equals() e hashCode() ganham seções próprias mais adiante, logo depois da busca dentro de uma lista.
44 · collections

Estruturas de dados

Estruturas de dados estudam formas de organizar, guardar e acessar informação. A gente já começou, sem perceber, com List e ArrayList.

  • ✓ Array / List / ArrayList
  • → Set / HashSet
  • → Map / HashMap
  • → buscas
  • → ordenação
  • → Big O básico

O assunto completo é bem maior (LinkedList, filas, pilhas, árvores, grafos...), mas para back-end essa é a ordem de prioridade que realmente importa no dia a dia.

Glossário

Uma cola de bolso com os termos usados nesta ficha, em uma frase cada.

Classe
O molde que define quais informações e ações um tipo de objeto vai ter.
Objeto
Uma instância concreta de uma classe, criada com new, com seus próprios valores.
Atributo
Um dado guardado dentro de um objeto (o "tem").
Método
Uma ação que um objeto sabe executar (o "faz").
Parâmetro
Um valor recebido de fora por um método ou construtor.
this
Referência ao objeto atual — usada sobretudo para diferenciar o atributo de um parâmetro de mesmo nome.
public / private
Modificadores que liberam ou restringem o acesso direto a um atributo ou método.
Getter / Setter
Métodos públicos para ler ou alterar um atributo privado.
Encapsulamento
O objeto protege seu estado interno e controla como ele pode ser lido ou alterado.
Construtor
Bloco especial, com o mesmo nome da classe e sem retorno, que inicializa o objeto ao nascer.
Sobrecarga
Vários métodos ou construtores com o mesmo nome, diferenciados pelos parâmetros.
Estado
O conjunto de valores que um objeto guarda em um dado momento.
Herança / extends
Relação "é um": uma classe filha herda atributos e métodos de uma classe mãe.
super
Chama o construtor (ou método) da classe mãe a partir da classe filha.
Polimorfismo
Uma referência de tipo geral pode apontar para um objeto de tipo mais específico.
Sobrescrita / @Override
Uma classe filha fornece uma nova implementação de um método herdado.
Abstração
Criar um conceito geral demais para existir sozinho, deixando os detalhes para as classes concretas.
Classe / método abstrato
Uma classe que não pode ser instanciada diretamente, ou um método sem implementação que as classes filhas são obrigadas a completar.
Associação / "tem um"
Um objeto guarda uma referência para outro objeto como atributo.
Encadeamento de métodos
Chamar um método sobre o resultado de outro, tudo na mesma linha (ex.: getCliente().getNome()).
null
Valor especial que indica que uma referência não aponta para nenhum objeto no momento.
NullPointerException
Erro que ocorre ao tentar usar um método ou atributo de uma referência que está null.
enum
Um tipo que representa um conjunto fixo e limitado de valores possíveis.
LocalDateTime
Tipo pronto do Java para representar data e horário juntos.
DTO
Objeto usado para transportar dados entre a API e quem a consome, sem expor a entidade real.
JPA / Hibernate
Tecnologia que liga as classes Java às tabelas do banco de dados automaticamente.
List / ArrayList
Uma coleção ordenada que guarda vários elementos do mesmo tipo; ArrayList é a implementação mais comum de List.
Índice
A posição de um elemento dentro de uma lista, começando sempre do 0.
for-each
Estrutura de repetição que percorre todos os elementos de uma lista, um de cada vez.
IndexOutOfBoundsException
Erro que ocorre ao pedir uma posição que não existe dentro de uma lista.
Object
A classe que fica no topo de toda hierarquia em Java; todas as classes herdam dela, mesmo sem extends explícito.
